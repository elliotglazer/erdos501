# The comparator challenges

This repository is laid out as a challenge for the Lean FRO's
[comparator](https://github.com/leanprover/comparator), the judge used by the
AIMO competitions, by [leanprover/lean-eval](https://github.com/leanprover/lean-eval)
and by the [Palomar registry](https://palomar-registry.org/how-to-submit).
Comparator guarantees, for every name in `theorem_names`, that the declaration
in `Solution` (i) has *exactly* the statement of the one in `Challenge`,
including every constant the statement mentions, (ii) uses no axioms beyond
`permitted_axioms`, and (iii) is accepted by the Lean kernel (and optionally by
the independent kernel `nanoda`).  It never trusts `Solution` — it rebuilds it
in a `landrun` sandbox and replays the exported environment through the kernel
in its own process.

There are two challenge pairs, with the same seven target names.

## 1. `Challenge.lean` / `Solution.lean` / `comparator.json` — Mathlib only

| file | role |
|---|---|
| `Challenge.lean` | trusted statements (`sorry`) — seven targets; **imports Mathlib only** (Palomar-conformant) |
| `Solution.lean` | the same statements proved by delegation to `Erdos501` (which imports `Flypitch4`); does not import `Challenge` |
| `Erdos501/FOL/Statement.lean` | Part A of `Challenge.lean` (the definitions) verbatim, generated by `scripts/sync-statement.py`; `Solution` proves statements about these constants, and the comparator checks that they are identical to the Challenge's |
| `comparator.json` | the challenge (all seven targets) — **passes** (2026‑08‑19) |
| `formalization.yaml` | metadata (mathlib-initiative `formalization.yaml` v0.4, Palomar conventions) |
| `lakefile.toml`, `lean-toolchain`, `lake-manifest.json` | the trusted build description (Mathlib pin) |
| `scripts/install-comparator-tools.sh` | installs `landrun`, `lean4export` (at our toolchain tag), `comparator`, optionally `nanoda` |
| `scripts/run-comparator.sh [config]` | `lake env comparator <config>` behind the recommended `systemd-run` wrapper |
| `scripts/sync-statement.py [--check]` | regenerate / check `Erdos501/FOL/Statement.lean` |

### Trusted base

Per the comparator's assumptions, "the transitive closure of imports of
`Challenge.lean` as well as `lakefile.toml` are controlled by you or
trustworthy".  Here that closure is **Mathlib** at the pinned commit
(`Mathlib.MeasureTheory.Measure.Lebesgue.Basic`, `Mathlib.SetTheory.Cardinal.{Continuum,Aleph}`,
`Mathlib.Data.Set.Card`, `Mathlib.ModelTheory.Satisfiability`, `Mathlib.SetTheory.ZFC.Basic`
and what they import) — nothing else.  What has to be audited by hand is Part A of
`Challenge.lean`, all of it definitions:

1. **The language** `L` (`Func`: `∅`, `ω`, `𝒫`, `⋃`, `(·,·)`; `Rel`: `∈`) and the
   depth-polymorphic combinators (`varT`, `allF`, `exF`, `andF`, …, `toSentence`),
   which build Mathlib `BoundedFormula`s with de Bruijn *levels*.
2. **The theory** `ZFC : L.Theory` — extensionality, empty set, ordered pairs,
   union, power set, infinity (`ω` is the least inductive ordinal), regularity,
   Zorn's lemma, and the strong collection scheme `collectionAxiom n ψ`.  This is
   Flypitch's axiomatization (Han–van Doorn), equivalent to the usual ZFC; every
   model of it is a model of ZFC.  `collectionAxiom` is the only definition with
   explicit de Bruijn arithmetic (`liftAt`); its docstring lists the level of every
   variable in each clause, and `Erdos501/FOL/Collection.lean`
   (`realize_collectionAxiom`) proves that its meaning in any `L`-structure is
   exactly "∀ params ∀ u, (∀ x ∈ u ∃ y ψ) → ∃ v, (∀ x ∈ u ∃ y ∈ v ψ) ∧ (∀ y ∈ v ∃ x ∈ u ψ)".
3. **The sentence** `Erdos501 : L.Sentence` — "every complete ordered field
   `(R, +, ·, <, 0, 1)`, given as sets, has the Erdős property", where the Erdős
   property is: for every function `A : R → 𝒫 R` (as a set of pairs) whose values
   are bounded (above and below) and of outer measure `< 1` (a cover by countably
   many open intervals `(aₙ, bₙ)`, `n ∈ ω`, whose partial sums stay `≤ r` for some
   `r < 1`), there is an infinite (`ω` injects into it) independent (`∀ x ≠ y ∈ X, x ∉ A y`)
   subset of `R`.  This is the single most important thing to audit; target 7
   reduces the audit to the audit of `zfsetStructure` and of the Mathlib-level
   statement (`Erdos501` in `ZFSet` ↔ the `formal-conjectures` proposition).
4. **The structure** `zfsetStructure : L.Structure ZFSet.{0}` — `∅`, `ZFSet.omega`,
   `ZFSet.powerset`, `ZFSet.sUnion`, Kuratowski `ZFSet.pair`, `∈`.

Then Part B: the seven statements, with `sorry`.  Independence is stated with
Mathlib's `Theory.ModelsBoundedFormula` (`T ⊨ᵇ φ`: every `ModelType` of `T` —
carrier in `Type 0` — realizes `φ`).  `¬ (ZFC ⊨ᵇ Erdos501)` therefore says that
some model of `ZFC` satisfies `∼Erdos501`, and `¬ (ZFC ⊨ᵇ ∼Erdos501)` that some
model satisfies `Erdos501`.  (By Löwenheim–Skolem — Mathlib's
`Theory.Model.isSatisfiable` — restricting to carriers in `Type 0` loses nothing.)

Everything else (`Erdos501/*`, `Flypitch4/*`, `Solution.lean`) is untrusted from
the comparator's point of view.

### How the Solution bridges to Flypitch (`Erdos501/FOL/`)

* `Translate.lean`: `trT`/`tr` translate `L`-terms/formulas (levels) into
  Flypitch `L_ZFC` bounded terms/formulas (indices: level `ℓ` at depth `n` ↦
  index `n - 1 - ℓ`); `toM S` makes a Flypitch structure an `L`-structure;
  `realize_tr`: realization commutes with the translation.
* `Axioms.lean`: `tr axiomOfEmptyset = axiom_of_emptyset` … `tr zornsLemma = zorns_lemma`
  are all `rfl`; with `Collection.lean` (the strong collection scheme, transferred
  semantically using the two-valued lift/substitution lemmas of `FolLemmas.lean`),
  `toM_models_ZFC : S ⊨ₜ ZFC_Flypitch → toM S ⊨ ZFC`.
* `Sentence.lean`: `tr_Erdos501 : tr Erdos501 = Erdos501_f := rfl`;
  `zfsetStructure = toM stdStructure`; hence target 7 from
  `stdStructure_realize_Erdos501_f_iff`.
* `Independence.lean`: Flypitch's completeness theorem gives, from
  `¬ (ZFC ⊢ₛ' φ)`, a nonempty two-valued model of `ZFC` with `¬φ`; via `toM`,
  `Theory.Model.isSatisfiable` and `Theory.models_iff_not_satisfiable` this is
  `¬ (ZFC ⊨ᵇ ·)`.

## 2. `ChallengeFlypitch.lean` / `SolutionFlypitch.lean` / `comparator-flypitch.json` — Flypitch's terms

The same seven results with targets 4–7 stated in the vocabulary of the vendored
Flypitch development: `¬ (ZFC ⊢ₛ' ∼Erdos501_f)`, `¬ (ZFC ⊢ₛ' Erdos501_f)`,
`independent ZFC Erdos501_f` (the exact shape of Flypitch's `independence_of_CH`),
`stdStructure ⊨ₘ Erdos501_f ↔ erdos501_deepmind`.  Its trusted base is Mathlib
**plus** `Flypitch4.Summary`, `Flypitch4.Erdos501.Sentence` and
`Flypitch4.Erdos501.StdSemantics` (the port's own validation is under
`third_party/flypitch4/`; `validation/Erdos501Print.lean` prints `Erdos501_f`).
It is not Palomar-conformant (the Challenge imports the vendored library) but is
kept because derivability in Flypitch's proof system is the stronger, syntactic
form of the result, and because it is what the forcing development proves
directly.  **Passes** (2026‑08‑19).

## Running

```sh
# once: toolchain + Mathlib cache
lake exe cache get          # requires network access to the Mathlib cache
lake build                  # everything, including both Challenge/Solution pairs

# once: tools
scripts/install-comparator-tools.sh   # needs go, and cargo for nanoda (optional)
export PATH="$PWD/.tools/bin:$PATH"

# judge
scripts/run-comparator.sh comparator.json           # prints "Your solution is okay!"
scripts/run-comparator.sh comparator-flypitch.json
```

Without `landrun` (e.g. macOS) a *non-sandboxed* dry run is possible with
`COMPARATOR_LANDRUN=.tools/bin/fake-landrun.sh`; that checks statements,
axioms and kernel acceptance but does not protect against a malicious
`Solution`.  Both configurations were judged this way on 2026‑08‑19 (comparator
`777e7f5`, lean4export at v4.34.0-rc1): "Lean default kernel accepts the
solution / Your solution is okay!"; CI runs the sandboxed judge.

## Toolchain constraints

* `lean4export` must be built with exactly `lean-toolchain` (olean headers are
  version-specific); the install script checks out the lean4export tag named
  after our toolchain.
* Comparator HEAD requires the challenge environment to define `eagerReduce`
  (Lean ≥ v4.34.0-rc1).  Bumping Lean/Mathlib later is fine; going back before
  v4.34.0-rc1 requires an older comparator (e.g. `71b52ec`, the lean-eval pin).

## Statement conventions

The seven statements are written so that a reader who trusts Mathlib can check
them against erdosproblems.com/501 by eye:

* hypotheses exactly as in `formal-conjectures`' `501.lean` (per-set
  `Bornology.IsBounded`, `volume.toOuterMeasure (A x) < 1`, closedness,
  `volume (A x) < 1`), conclusion `X.Pairwise (fun x y => x ∉ A y)`;
* `erdos501_closed_size3` says `3 ≤ X.ncard` (`Set.ncard` is `0` on infinite
  sets, so this is a *finite* independent set with at least three elements;
  `erdos501_closed_infinite` gives the infinite one);
* `erdos501_hechler_of_CH` takes `CH` as `(ℵ₁ : Cardinal.{u}) = 𝔠` (a universe
  parameter `u`; all universes are equivalent through `Cardinal.lift`);
* `erdos501_not_refutable` / `erdos501_not_provable` are `¬ (ZFC ⊨ᵇ ∼Erdos501)` /
  `¬ (ZFC ⊨ᵇ Erdos501)` (`∼` is Mathlib's `BoundedFormula.not`), and
  `erdos501_independent` is their conjunction; in the Flypitch pair,
  `¬ (ZFC ⊢ₛ' ∼Erdos501_f)` / `¬ (ZFC ⊢ₛ' Erdos501_f)` / `independent ZFC Erdos501_f`
  (`bd_not` is Flypitch's `∼`).
